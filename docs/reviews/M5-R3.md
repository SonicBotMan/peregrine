# M5 R3 反思 — MCP 服务器（Agent 原生层）

日期：2026-09-14 · 前序：R1（自查）→ R2（独立审查）→ 处置（M5-R2-disposition.md）→ 本轮

## 本轮做对了什么

1. **薄代理原则贯穿到底**。10 个工具零业务逻辑，全部是 REST 调用的类型化包装；queue/throttle/resume 语义只活在 scheduler 一处。v1 的教训（GUI 重实现调度逻辑导致两脑漂移）在第三个客户端（GUI/CLI 之后）上没有复发。
2. **错误契约先想清楚再写码**。「daemon 失败 = tool error（模型可见），unroutable = 协议错误」两分法在第一天就定下，测试直接按契约写（unknown-task、daemon-down 两个专测），R2 审查没有在这块发现任何问题。
3. **R1 的 panic 修复是真正的 P1**。外部模型的任意输入走到 `unwrap_or_else(panic)` —— 这是把「客户端可信」假设带进了 Agent 原生层。修掉后整个 dispatch 对任意 JsonObject 都安全。
4. **R2 的 P1-1 用源码证据反驳而非盲修**。审查者怀疑 list 慢查询，实际是带索引的单条 SQL；写时长断言测试只会引入 flaky。「不修 + 记录证据」比「加防御性测试」更优雅。

## 教训

1. **rmcp 3.3 的 `serve_server()` 对 raw duplex 会死锁**（R1 #4：测试挂死 600s）。官方测试用 `ServiceExt::serve`。SDK 版本差异（2.x→3.x）的坑在文档稀疏区，只有真跑才知道——集成测试先写「配对握手」再写业务断言，能最早暴露这类问题。
2. **clippy autofix 会在我 edit 的同时改文件**，导致后续 oldText 漂移（本轮撞了两次）。对策已形成肌肉记忆：edit 失败立即重读文件，绝不信内存里的内容。
3. **对模型输入的宽容要放在边界**。大小写归一放在 MCP tools.rs（String→normalize→REST），REST 契约保持严格——而不是把 serde alias 加进 api crate 让所有客户端共享宽容。边界宽容、内核严格，比反过来好测试也好推理。

## 优雅性终评

- 交付面：4 源文件 ~700 行 + 6 集成测试，全部真 daemon 栈配对验证。
- `settings://` 只读无推送如实写进资源描述，不装作有推送。
- 每个工具的 schema/description 都写到「模型第一次调用就能给对参数」的程度（本轮 P1-3 修复后）。
