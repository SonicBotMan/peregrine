## P1（应修）

**P1-1 写点 check-then-act 复用了会清空 total 的 upsert 语义**
`crates/engine-http/src/download.rs:438-441` + `crates/storage/src/lib.rs:144-146`
写点先 `get_task`（None 时）再 `upsert_task(url, sink, None, Some(&wire))`，而该 upsert 的 SQL 是 `ON CONFLICT(url,sink) DO UPDATE SET total = ?3` —— **无条件把 total 覆写为 NULL**。若两次调用之间另一方（segmented 会话的 `replan`，segment.rs:543）先建了 total=Some 的行，本侧 upsert 会把 live segmented 行的 total 打成 NULL：Route 1 随之失明，后续同 (url,sink) re-add 走 probe→replan 全量重下（浪费），或带 resume ctx 时对稀疏文件走单流 append（靠 append 长度校验/416 自愈兜底成可见错误）。
**可达性**：daemon 内不可达 —— scheduler 有 path 级互斥（scheduler/lib.rs:651-660 busy_paths）且 add() 拒绝重复 (url,path)；但 engine-http 是公开 library crate，库用户并发驱动同一 Store 的两个会话即可命中。修复廉价：专用 SQL `INSERT ... ON CONFLICT(url,sink) DO UPDATE SET etag=?4`（不碰 total），语义即"validator-only 创建/刷新"。鉴于修复成本极低且属于公开 API 面上的状态机缺陷，定 P1。

## P2（建议）

**P2-1 `upsert_task` 后跟冗余 `set_validator`**
`crates/engine-http/src/download.rs:440-441`。插入路径 upsert 已写入 etag，再 set_validator 是第二次 spawn_blocking 往返；顺带 `Err(e) => Err(e)` 两处空臂可简化。纯效率/整洁。

**P2-2 `from_wire`/`wire` 无单元测试；集成测试只覆盖 strong-etag 路径**
`crates/api/src/download.rs:56-73` 新增的形状启发无任何单测；4 个集成用例（validator_resume.rs）的 mock 只发引号强 etag。未覆盖：①弱 etag `W/"…"` → None 拒绝；②Last-Modified wire 往返；③畸形未引号 etag 的 enum 变体漂移（存时 `StrongEtag("v1")`、重建为 `LastModified("v1")` —— wire 输出相同故惰性无害，但值得测试锁定）。建议补 api 层单测 3-4 条。

**P2-3 降级路径的键漂移（final URL vs original URL）**
fresh segmented 会话在 `auto.rs:118-121` 已把 `job.url` 改写为 probe 的 final URL；若其触发 `SingleStreamRequired` 降级，`run_with_downgrade` 末尾的 `engine.download` 写出的 validator-only 行以 **final URL** 为键，而后续 resume 用 `task.url`（original，scheduler/lib.rs:933）查不到 → 退化为无 validator 续传（安全方向，功能漏覆盖）。与 R1 自查"写/读键均为 original"的结论不符——该结论只对 Route 2 直连路径成立。可记入 R1 已列的"重定向行键统一"遗留项。

**P2-4 镜像 etag 抖动的性能边角**
validator 取自 final response（redirect 后）但行键在 original url 下（download.rs:438）。若 original 轮换重定向到 etag 按实例生成的镜像（Apache FileETag INode 类），每次 resume 都 If-Range 失配 → 200 全量重放。永不损坏（方向安全），仅浪费；可考虑按 final_url 键或行内存 (validator, final_url) 对。

**P2-5 `ctx.validator.is_none()` 优先级：caller 胜过 row**
`crates/engine-http/src/auto.rs:87`。生产路径 `resume_job` 恒传 None（scheduler/lib.rs:926-931），无实际冲突；但语义上 row 是上一会话首响应写入、通常比 caller 手里的更鲜。现优先级在最坏情况只多做一次安全全量重放，可接受；建议 doc 注明理由。

**P2-6 测试小项**
`validator_resume.rs:126-133` `engine(name)` 的 name 参数未用（`let _ = name;`）；test 2/3 手工 seed 行而非跑真实首会话（写侧已有 test 1 覆盖，可接受）；mock 对 `start >= len` 回 200 而非 RFC 的 416（未测路径，不影响本组断言真实性）。

**P2-7 已知残余缺口（非 B36 回归，建议记录在案）**
(a) 只发 Last-Modified 的资源 + 忽略 If-Range 只认 Range 的服务器 → 206 粘接时 etag 双保险不生效（download.rs:397-413 的 guard 需响应带 ETag）——B36 前后行为等价；(b) persist(新 validator) 与 open_sink(Truncate) 之间的崩溃窗口：旧 body 全量在盘 + 新 validator 恰好匹配 → 粘接，同样与 B36 前等价（DownloadJob.resume doc 已声明）；(c) LM 1 秒粒度同秒修改，from_probe 文档已接受。

## 七个审查点逐答

1. **写点位置** ✔ 正确。server_total 融合后、open_sink 前：resume/200-truncate 会话持久化的恰是"当前响应"的 validator（方向正确）；416 两个分支（settle-complete / heal 递归）均在其之前早退，healed 递归透传 vstore（download.rs:326）由新 200 自行落库；redirect 下键=`url`（job 原 URL，非 `current`/final），与读侧 `job.url` 一致——唯 P2-3 降级路径例外。
2. **往返保真** ✔ `wire()` 原样输出、`from_wire` 引号→etag / 其他→LM，往返稳定；弱 etag 有双保险（写侧 `response_validator` 过滤 `W/` + from_wire 拒绝）；LM/畸形误判最坏后果都是 no-match If-Range → 200 安全全量重放，不会走向粘接。
3. **读点** ✔ `existing.clone()`（auto.rs:53）是读侧复用所必需，TaskState clone 廉价；Route 1（total Some）先行保证 segmented 行绝不进入 Route 2；caller-validator 优先级安全（P2-5）。
4. **行交互** ✔ segmented 会话经 `replan`（segment.rs:543-556）用 `upsert_task(Some(total))` + `set_validator` 升级/清洗 validator-only 行，且 stale 判据 `t.total != Some(total)`（segment.rs:253）强制 replan，残行不会干扰 segmented；单流完成后的残行对 re-add 无害（重 add 走 probe→replan 全量重下，与 B36 前无行为差异；同长文件则 416-settle 即时完成）；残行有清理 owner（scheduler purge→port purge 按 (url,sink) 清含 total-NULL 行）。
5. **daemon 装配** ✔ `Store` 是 `Arc<Mutex<Connection>>`，`with_validator_store(store.clone())`（daemon.rs:202）与 HttpAutoPort 的 store 同一实例，这正是 B36 读写闭环的必要条件（B32 单 Store 规则）；`build_with_port` 测试路径不接、按设计退化。无所有权/生命周期问题。
6. **测试真实性** ✔ 无假绿。test 3 的字节级断言是真实判别器：若读侧缺失，mock 会 206 粘接 v1 前缀 → 断言必挂；mock 对已测路径忠实于 RFC 7233（If-Range 强比较精确匹配；失配即忽略 Range 回 200）。缺口仅为弱/LM 路径无覆盖（P2-2）。
7. **lock/await/吞错/SQL** ✔ 写点无任何 guard 跨 await；store 方法均为 spawn_blocking 内同步持锁（clippy 0 warning 佐证）；唯一吞错是设计内的 best-effort warn（download.rs:447-450）；SQL 状态机唯一瑕疵即 P1-1。
