# 轮B R1 自查（B59：BT 跨重启 purge 侧表）

对象：未提交 diff（engine-bt lib.rs + Cargo.toml、scheduler bt_port.rs、daemon.rs）。约 +150 行。

## 设计

- **问题**（B59, M4-b2 R2' P2）：BT registry 是内存态，重启即空；`.torrent` 行的 hash 无法从 url 推导，跨重启 purge 只能 remove_sink(sink) 兜底——数据目录（output_folder = sink.parent()）里的其余文件永久泄漏。
- **修法**：Registry 持久化 `url → output_folder` 侧表（json，daemon 数据目录 `<stem>-bt-registry.json`，全量重写）。
  - `register()` 成功 → `folders.insert` + flush（含 Some 分支 refcount++ 路径——尾部统一 insert，幂等覆盖）。
  - `detach()` 走到 Last（引用归零，无论 session delete 成败）→ `folders.remove` + flush；Held 不动侧表（兄弟任务还引用）。
  - `purge()` Unknown 分支（跨重启）：先查侧表 → `remove_sink(folder)`；条目消费后 flush。之后原有 magnet-hash 兜底与 remove_sink(sink) 保持不变。
  - `BtEngine::with_registry_persistence(path)` builder（load 时机=构造）；`BtAutoPort::with_registry_persistence` 透传；daemon assemble 用 `store_path_with_suffix(&db_path, "bt-registry.json")`。
- **语义边界**：
  - 侧表只在 Unknown（内存无映射）时被消费——同 session purge 走 Last 路径删 session entry+数据（session.delete(purge_files)），侧表条目同步清除，不重复删。
  - flush best-effort（warn 不失败下载）；load best-effort（损坏=空表）。
  - 多 daemon 实例共享同文件：全量重写有丢更新窗口——与 tasks.db 单写者假设一致（同目录同生命周期，一个数据目录一个 daemon），不额外加锁。

## 自查

- register 的 Some(meta)（同 torrent 复用）分支也刷新侧表 ✓（尾部统一 insert 覆盖同键）。
- purge Unknown 且侧表命中且 by_hash 也命中（同 url 既是 .torrent 又碰巧 magnet 可解析？file:// url 不可能）→ 互斥场景不成立 ✓。
- 侧表条目泄漏路径：任务行被用户 remove（走 purge_files=false？）——查 purge 调用链：remove 硬删任务 → purge(url, sink, true)。若 purge_files=false（仅删行不删文件？）侧表条目残留 → 下次同 url 跨重启 purge 会误删已不被引用的 folder。**存疑点①**：purge_files=false 时是否也该消费侧表条目？——是。查 scheduler 端 purge 语义后定（若 false 仅用于「取消任务」语义则不该删）。
- 测试：b59_cross_restart_purge（侧表命中删 folder + 条目清）、b59_side_table_entry_freed_on_regular_purge（同 session Last 路径清条目）。覆盖主路径；未覆盖 flush 失败降级（人为 chmod 故障注入成本高，warn 已声明 best-effort）。
- daemon `store_path_with_suffix`：`peregrine.db` → `peregrine-bt-registry.json`，同目录 ✓；无扩展名/裸文件名边界处理 ✓。

R1 结论：可交 R2（重点：存疑点① purge_files=false 的侧表语义；folders 覆盖窗口；flush 全量重写放大）。
