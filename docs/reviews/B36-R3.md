## 教训

1. **复用既有 upsert 前先读它的冲突臂**——R1 的 get_task→upsert_task 组合在"行不存在"分支上安全，但 upsert 的 `DO UPDATE SET total=?3` 语义会把并发建好的 segmented 行 total 打成 NULL。复合 SQL 的冲突臂是隐式契约，R1 只看了调用侧没看被调侧。
2. **键一致性断言必须枚举所有写点路径**——R1 结论"写/读键均为 original"只对 Route 2 直连路径成立；segmented→降级路径写出的行键是 final URL（R2 P2-3）。自查时宣称"一致"前应逐路径列表核对，而非凭主路径印象。
3. **公开面可达性 > 当前调用方可达性**——P1-1 在 daemon 内不可达（path 互斥 + add 去重），但 engine-http 是公开 library crate，库用户并发即命中。修复判定标准应是"API 面上是否可构造"，不是"我们会不会这么用"。
4. **R1 阶段就抓到 total=NULL 设计缺陷**（首版写点带 server_total 会被 Route 1 误判）说明"先想清楚行状态机（validator-only 行 vs segmented 行）再写 SQL"的顺序正确；状态机判据（total IS NOT NULL）应写进 doc 注释固定下来（已写）。
