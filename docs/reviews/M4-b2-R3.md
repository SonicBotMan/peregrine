## 教训

1. **「共享资源 + 引用计数」是缺陷温床**：本轮 2 个 P0 + 修复中发现的第 3 个级联缺陷（Held 删映射）全部出在同一主题——多个任务共享一个 session entry 时的 purge 语义。第一版设计（HashSet 计数 + Option 返回值）在三个维度各错一次：计数单位错（url 去重 ≠ 任务数）、返回值语义错（None 无法区分 Unknown/Held）、状态清理时序错（Held 时删映射）。**设计这类结构时先写状态机表（url_to_id × id_meta.urls × session entry 三层状态的所有合法转移），再写代码**——三个缺陷本可在一页纸上全部显形。
2. **回归测试要在修复前先写**：`same_url_two_sinks_refcounts_purge` 写完后立刻抓到了我修复代码里的级联缺陷（detach-Held）。如果按惯例"修完再补测试"，这个缺陷会安静地活到下一轮 R2。
3. **write 工具静默回滚在本轮第 4-6 次出现**（package.sh 报成功但盘上无文件）。已固化流程：关键写入后立即 `wc -c`/md5 校验，bash heredoc 为兜底通道。这不是 peregrine 的缺陷，是开发环境的系统性问题——但它污染过审查记录（R1 文档两度失真都与此相关），值得在会话记忆里保持警戒。
4. **P1 的时序决策**：remove-即删-数据与 M5.1 P0-2 同源，选择"本提交最小安全改动（BT 默认不删数据）+ 完整贯通留给 M5.1"而非抢跑重写 purge 契约——避免半套契约两处维护。破坏性操作的默认值宁可保守（不删），贯通时一次做对。
5. **打包（M6-a）提前落地的代价控制**：tarball/deb/version/strip 全链 30 分钟内完成，靠的是"最朴素方案优先"（cargo build+tar 而非 cargo-dist；cargo-deb 只因 deb 是 Linux 分发硬通货）。systemd unit/CI 发布链留给 M6-b，不膨胀本轮范围。
